# Task 2.4 — Operation-specific character authority

**Status:** Conversational design approved by the owner on 2026-09-28; written specification awaiting owner review. Task 2.4 is not implemented.

## Intended outcome and scope

Every later character command must decide authority from the currently verified login and private database state inside the transaction that commits the command. A living character's ID, an old API response, a signed-in session, or a client-supplied life state is not permission to act. An incapacitated character retains the one-living-character slot but loses ordinary action authority. Permanent death never restores the former character's authority. A cooldown observer can inspect their own records and public material without acting as the dead character.

The owner approved a distinct **game-moderation restriction**: a restricted game account may inspect its own private records and use out-of-character account support, but cannot create a character or take character actions. A provider-level ban or invalid/recovery-only session remains governed by Supabase Auth and the existing API boundary; it does not become a game observer session. Any active or suspended operator assignment remains operator-only for player APIs. This task establishes the policy boundary; it does not build a moderation console, support system, rescue mechanic, dead-record UI, or gameplay domain.

Task 2.3's creation feature control stays false in managed development. Task 2.5 owns onboarding and System presentation; Task 2.7 owns own-record and observer views. Later life/death and moderation services own attributable transitions, and each future domain owns its additional action requirements.

## Approaches considered

1. **Shared transaction-level authority guard (chosen).** Named operations receive one consistent actor/account/character decision after current rows are locked. Each command service still validates its own ownership, location, resource quantities, rules and version in that same transaction. This avoids copy-pasted state checks while keeping domain decisions specific.
2. Route-level middleware alone would give a convenient early denial but cannot close a race where restriction or death commits before a later action commits. It may improve presentation, but it cannot be the authoritative guard.
3. One large SQL function for all future actions would centralize policy but entangle identity, combat, trade, rewards and content as those domains grow. Narrow SQL helpers for otherwise inaccessible Auth rows remain appropriate; the operation policy belongs in a small server/database module with explicit callers.

## Private state and projections

Add a constrained `active | restricted` game-account access state, defaulting to active, in a single canonical SQL migration. It is separate from Supabase ban/deletion, operator assignment, character life, awakening, presence, public visibility and cooldown. Only the trusted migration owner can change this state in Task 2.4; `hunter_runtime`, public API roles and clients receive no grant to set or clear it. A later audited moderation service must record reason, actor and time when it adds a mutation path; if the login has no game-account row yet, that service must link or create one before applying a restriction. `GET /v1/me` remains read-only and never provisions an account. The migration must keep `game` outside the exposed Data API schemas and preserve the existing narrow runtime grants.

The private `GET /v1/me` response advances its schema version and reports a coarse `onboarding | active | incapacitated | observer | restricted` mode plus creation eligibility. `restricted` takes precedence over a living-character mode and yields `creation.status = restricted`; its existing owner-only living-character projection may remain readable. `observer` means no living character and either dead character history or a stored cooldown; expiry of cooldown alone does not reactivate a dead character. A never-played account with no living or dead character remains `onboarding`. The response does not disclose a dead-character dossier, other account IDs, moderation reason, provider status, hidden awakening evidence or precise location. Task 2.7 will expose historical own records through a separately authorized private projection.

This response is presentation evidence, not an action token. `POST /v1/characters` must independently deny `restricted` accounts before creating an account, inserting a character or disclosing a prior receipt. Feature-disabled, occupied and cooldown behavior otherwise retains Task 2.3 semantics. The existing Auth verifier continues to deny invalid, recovery-only, OTP-only, banned, deleted or unverified identities as appropriate. Route errors are stable and do not include private account or character details.

## Authority policy and transaction boundary

The shared guard takes the current verified Auth UUID, an explicitly named operation, and the requested character ID and expected revision when that operation acts as a character. It returns either a minimal, transaction-scoped authorized context or a typed denial. It is called with the same PostgreSQL client and transaction used by the caller's eventual mutation. Unknown operation names fail closed. A broad `isLoggedIn` or `isAlive` result cannot authorize a command.

Initial policy names cover `account.records.read`, `public.content.read`, `character.create`, `character.profile.update`, and `character.rescue.respond`. Read-only account support uses an out-of-character policy, not dead-character authority. The last two names establish explicit policy behavior for later endpoints; they do not create profile or rescue endpoints now. Future trade, reward, encounter, guild and other operations must add named policy entries with their own tests and then perform domain checks in the same committing transaction. `character.rescue.respond` is denied by default until an explicit rescue rule and endpoint exist; incapacitation never grants generic self-rescue or inventory use.

For a mutation, the guard follows the existing operator-assignment advisory lock first, then any needed feature-control lock, the private locked Auth eligibility check, the linked game-account row, and the owned character row. It locks account and character rows strongly enough that concurrent restriction, ownership/life or revision changes cannot commit between the decision and the action. It verifies the character belongs to the resolved account and compares the expected revision to the current database revision. A mismatch returns a stale-state denial; the caller must fetch confirmed state and make a new decision. The guard does not trust client-supplied account, life, moderation, presence or cooldown data. Future writers of restriction and life state must coordinate with this lock order and advance revisions. Provider or database errors fail closed and do not appear as eligibility.

Policy outcomes are deliberately narrow:

| Current state                                          | Private own records / support   | New character                                            | Ordinary character action     | Rescue response                                     |
| ------------------------------------------------------ | ------------------------------- | -------------------------------------------------------- | ----------------------------- | --------------------------------------------------- |
| Eligible account, no character                         | Allowed                         | Allowed only if feature, slot and cooldown pass          | Denied                        | Denied                                              |
| Alive character, active account                        | Allowed                         | Denied by occupied slot                                  | May proceed to domain checks  | Denied unless a future rule explicitly changes this |
| Incapacitated character, active account                | Allowed                         | Denied by occupied slot                                  | Denied                        | Denied until a future explicit rescue rule exists   |
| Dead history / observer, active account                | Allowed                         | Allowed only after cooldown and all creation checks pass | Denied for the dead character | Denied                                              |
| Game account restricted                                | Allowed                         | Denied                                                   | Denied                        | Denied                                              |
| Provider banned/deleted, invalid or restricted session | No authenticated private access | Denied                                                   | Denied                        | Denied                                              |
| Operator-assigned login                                | Player APIs denied              | Denied                                                   | Denied                        | Denied                                              |

Public content remains governed by its own visibility and moderation rules; this table does not make private records public. An authenticated observer may read public content where any eligible reader can. The policy does not grant posting, trade, rewards, voting or guild commands to dead, incapacitated or restricted identities.

## Failure, concurrency and evidence

Use typed denials for missing/foreign character, stale revision, restriction, incapacitation, death/observer, operator-only and ineligible provider state. Map them to safe API responses only where an endpoint exists; do not leak whether another account owns a guessed character ID. Do not cache a successful guard result across requests or use it after the transaction ends. A retry must be reauthorized from current state before any historical receipt is returned. Reconnect fetches confirmed state; it never silently replays offline game mutations.

Meaningful real PostgreSQL tests must show: a foreign character ID cannot act; a stale revision cannot act; alive can reach domain checks but not bypass them; incapacitated and dead cannot take ordinary actions; a cooldown observer and a restricted account retain only the approved reads; a restricted account cannot create or replay a creation receipt; provider/operator exclusions remain intact. Two-connection races must prove that an action either commits before a competing restriction/death transition or observes it and denies, never commits afterward under stale authority. Exercise both lock orderings and inspect durable state, not only returned decisions. Verify runtime/public grants and migration checksum replay. Unit/API tests cover the private `/v1/me` mode and safe errors. Preserve the existing account/recovery/operator browser journeys.

Completion requires focused and full local checks, independent Sol review, disposable PostgreSQL concurrency evidence, clean CI, reviewed managed-development migration read-back, and the deployed API revision/boundary checks applicable while the feature flag is off. No live authenticated character action or support workflow exists yet, so neither Task 2.4 nor Phase 2 may claim playable gameplay or public lethal readiness.
