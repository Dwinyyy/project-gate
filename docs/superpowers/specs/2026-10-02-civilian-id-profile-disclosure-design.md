# Task 2.6 — Civilian ID and profile disclosure

**Status: PROPOSED — awaiting written owner approval.** This document specifies behavior; it authorizes no implementation, dependency installation, managed mutation, deployment or commit. Task 2.5 is complete. Phases 0–1 are complete; Phase 2 remains active, with 17 completed tasks overall and 32 unfinished tasks through the approved Phase 6 prototype boundary. A persistent civilian identity is verified; playable gameplay is not available.

## Intended experience and selected constraints

A registered civilian can open an arm's-length-readable ID from persistent quick access, show or conceal it voluntarily, and choose the limited identity information another player may see. They may deliberately generate a temporary QR or share an opted-in public profile link. Every online profile requires an eligible signed-in player; the owner selected **no anonymous profiles and no search/directory**. A private owner view and in-person card remain usable without online disclosure.

Signup, civilian creation and this ID require no real photo. The card uses the registered alias, a neutral **Civilian** identity presentation and, only if selected for disclosure, the existing fictional avatar and calendar registration date. It invents no rank, class, professional credential, official photo verification, guild membership, title or achievement. Post-awakening official Hunter/Association ID registration belongs to a later design. An awakened character receives an honest unsupported-official-ID state here, never a fabricated civilian or Hunter card.

Task 2.6 implements privacy-controlled projections and `profile.view` QR invitations only, through a separate closed-by-default managed-development pilot. The audience choice is a privacy design decision, not blanket permission for a broad release. Party, trade and friendship invitation actions belong to Tasks 8.2, 10.2 and 11.5 and have no working buttons, token scopes or handlers in this feature. Photo storage/generation, associations, map presence/location, funds, equipment, combat and death-transition services remain outside this design. Existing account/recovery/TOTP, one-living-character enforcement, hidden awakening, private schemas and server authority remain intact.

Interpretation confidence is high following the owner's audience choice. Coding difficulty is moderate integration across existing contracts, database services, API and session-aware player UI. This is an architectural task: written-spec approval precedes an implementation plan and its execution-method selection. Parent/integration owner controls those gates and the shared contracts/canonical migration.

## Approaches and tradeoffs

1. **Signed-in known-link sharing — proposed.** Private is owner-only online; limited requires a deliberately issued temporary token; public permits a known stable profile link. All outward views use the same selected field allowlist and require current eligible player authentication. There is no directory, search or automatic discoverability. This gives the existing three visibility values distinct meanings without building social relationships early.
2. **Recipient-bound limited sharing.** A temporary token additionally names one recipient. Forwarding is less useful, but choosing/identifying recipients and managing acceptance adds a social flow absent from this phase. It is excluded from the proposed implementation. A limited bearer token can be forwarded to another eligible signed-in player; the interface must not promise otherwise.
3. **Anonymous public web profiles.** This would broaden sharing outside the app and expose an anonymous read surface. The owner's signed-in-only choice excludes it.

The proposed QR is an invitation to read selected identity information. Possession never grants gameplay authority, private data permission, a relationship, proximity or a trade authorization. Received information and saved images cannot be recalled; revocation prevents later server disclosure. All outward visibility below additionally requires the independent profile-disclosure pilot gate to be on; stored consent alone does not imply current availability.

## Persistent state and exact projection boundaries

Keep `/v1/me` schema v3 as the existing private owner contract. Add separate versioned exact DTOs for owner profile settings, outward civilian projection, invitation metadata, operation receipts and mutation outcomes. Both route schemas and client parsing reject unknown fields. Owner and receiver DTOs are separate types; never spread the owner character object into an outward response.

One canonical SQL migration extends `game.characters` beside existing `profile_visibility` with two constrained booleans defaulting false, a nonnegative disclosure revision and a unique independent opaque public reference. A separately generated random UUIDv4 is sufficient for the public reference; it is not the internal character UUID, is not a secret and does not authorize reads. Clients never select the reference or disclosure revision. Existing rows are explicitly backfilled by the migration; future character defaults create private/off settings without a second schema runner or lazy public-read write. Existing character revision remains an exact decimal string in API control data. The same migration adds an independent `profile_disclosure` feature control defaulting **false**; it never enables character creation, encounters or commerce.

Add private `game.profile_invitations` with issuer account/character ownership, fixed scope `profile.view`, a 32-byte token digest, disclosure revision at issue, server creation/expiry timestamps, revocation timestamp, operation identity and rule version. Maintain at most one nonrevoked token per character/scope; expiration does not itself mutate a row, so issuance revokes any previous nonrevoked row before insertion. A digest is unique. No raw token is persisted.

Add append-only `game.profile_operation_receipts`, keyed by resolved account and operation UUID, with operation kind, canonical SHA-256 request digest, subject, rule version, committed time and recorded result metadata/versions. Issuance metadata identifies the invitation and original expiry but contains no raw token. Receipts provide durable event evidence of privacy changes, issuance, replacement, revocation and withdrawal, rather than relying on logs. They cannot be rewritten or deleted by the runtime. No generic invitation/capability/event framework is introduced.

Keep `game` private and outside the exposed Data API. Runtime grants permit only needed columns and receipt/invitation operations. Public roles receive no schema/table/function access; the runtime receives no account restriction, ownership, life, awakening or presence mutation grant. Every migration function revokes default PUBLIC execution in its transaction and uses a pinned search path where relevant. Actual migration checksums, grants and deployment evidence are verified later, never inferred from this document.

The owner profile snapshot contains schema/rule version, current own living-profile settings, private character/disclosure revisions, current preview and current invitation metadata; no raw secret is returned by reads. It distinguishes no living profile from unsupported official-ID state. Outward successful DTO contains only schema version, alias, `Civilian` presentation, optional disclosed avatar and optional registration date. Resolve success may include invitation expiry as invitation metadata, not an authority or life claim. Public profile response needs no internal ID, policy details or character revision.

## Proposed API contract

| Endpoint                                  | Inputs                                                                                                          | Result and authority                                                                                                        |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/me/profile`                      | Current standard player bearer                                                                                  | Current owned living-profile settings/preview and invitation metadata; own-record read policy                               |
| `PUT /v1/me/profile`                      | Owned character ID, expected character revision, complete visibility/avatar/date draft; operation UUID header   | Recorded receipt plus distinct current state; named `character.profile.update`                                              |
| `POST /v1/me/profile/invitations`         | Owned character ID, expected character revision, fixed scope and `generate` or `replace`; operation UUID header | Receipt/current metadata; raw token delivered only on first successful issue; named `character.profile.invitation.issue`    |
| `POST /v1/me/profile/invitations/revoke`  | Owned character ID, expected character revision; operation UUID header                                          | Revoke current temporary disclosure and rotate public reference; receipt/current state; named ordinary character revocation |
| `POST /v1/me/profile/disclosure/withdraw` | Exact fixed account-wide withdrawal request; operation UUID header                                              | Monotonic stop-sharing of all owned profiles/tokens; minimal receipt; `account.disclosure.withdraw`                         |
| `GET /v1/profiles/:publicReference`       | Opaque reference and current standard player bearer                                                             | Current approved outward DTO only when currently public and supported                                                       |
| `POST /v1/profile-invitations/resolve`    | Token in bounded JSON body and current standard player bearer                                                   | Current approved outward DTO and expiry metadata; read-only                                                                 |

The owner mutation responses deliberately separate `receipt` (what the operation committed) from `current` (what exists now). `replayed` describes a historical effect, never reapplication. `tokenDelivery` distinguishes a new secret delivered now from a recorded issuance whose secret is unavailable. After successful or replayed writes, the UI renders confirmed current state, not historical receipt settings. No endpoint accepts client-selected account identity, life, proximity, authority, reward, image URL or expiry.

All routes retain safe request IDs, `no-store`, bounded bodies and stable sanitized errors. Initial limits follow established route patterns: owner reads/public profile/resolution 60 per minute per API limiter identity; owner mutations 20 per minute, alongside existing global limits. These are bounded abuse controls, not a substitute for permissions or production load verification. Actor-scoped mutation limiting is added using current verified identity where the installed limiter supports established patterns. Unknown route/scope/extra fields fail closed.

## Transaction, replay and current authority

Use a focused profile database service called by API and any future worker. Follow established operator advisory lock, applicable feature-control lock, Auth eligibility/pilot-grant lock, account, character, invitation and receipt ordering for new writes. Mutation authority and domain checks run on the same PostgreSQL client that commits. Ordinary writes take the owned character **FOR UPDATE initially**, not a shared lock followed by competing upgrades. Unknown operation names deny. A pure owned-receipt replay instead uses account-owned-record read authority; do not run a profile-action guard or acquire a profile-write lock merely to read historical metadata, which would deny approved reads or conflict unnecessarily with withdrawal.

For a new ordinary profile publication/issue/revoke, the actor must currently be provider-eligible, a non-operator, own the specified character, have an active game account and an alive character. New profile publication/settings writes and QR generation/replacement additionally require a supported unawakened Civilian ID, the profile-disclosure gate and the current existing designated pilot grant, locked inside the committing transaction. This reuses `ops.character_pilot_access` solely to authorize this bounded disclosure pilot; it confers no new character-creation, operator or gameplay authority and adds no new allowlist framework. Issuance additionally requires limited/public visibility. Incapacitated, restricted and dead/observer actors cannot publish or issue. The existing character-creation switch stays **off** throughout Task 2.6; its closed state does not erase the accepted civilian identity. Token revocation and account-wide withdrawal remain reduction-only operations and do not require the external-sharing gate. New-action policy applies only after an authorized account-owned receipt lookup has found no matching committed operation.

Within the transaction, revalidate the current provider-eligible non-operator actor and resolved account ownership under account-owned-record read authority first. Check the account-scoped operation receipt and canonical digest **before comparing a new-action expected revision or applying publication/issuance authority**: the original successful operation may already have advanced that revision. Same UUID and different terms/operation/subject is a conflict once owned-receipt lookup is authorized, regardless of whether current character-action policy would allow a new write. A matching receipt is readable by its current authentic account owner even while game-restricted, incapacitated, dead/observer, gate-off or grant-revoked. It returns only recorded operation metadata/versions, never raw secret, old disclosed fields, dead dossier or write authority. It never reinstalls prior settings, token, reference or expiry.

Evaluate the separate `current` field using current own-profile read policy: the supported living owner can still receive their private current settings/card; a dead/unsupported subject has no current usable card, and gate-off always reports outward sharing unavailable. Historical receipt permission never widens this projection. A no-receipt new action must pass full named action policy, current ownership, exact expected revision and applicable gate/grant before writing. After acquiring the new action's serialization locks, recheck the receipt before expected revision so simultaneous identical UUIDs replay the first commit rather than treating its version advance as stale. A new operation UUID at the older expected revision is stale. Keep decimal revisions as strings, including values above JavaScript safe integer range.

Each new committed profile update advances character and disclosure revisions, invalidates temporary tokens and records receipt evidence atomically. Audience transitions rotate the public reference; toggling avatar/date while remaining public retains the known reference but every read applies the current field policy. Explicit token revocation also rotates the public reference, advances versions and leaves selected visibility unchanged. Account withdrawal sets all owned profiles private, revokes temporary tokens, rotates public references and advances affected current versions. Later private→public transition creates a fresh reference, so a past public link cannot silently reactivate. **Every newly committed Generate or Replace advances both character and disclosure revisions atomically**, revokes the previous nonrevoked invitation row if present, and records the new invitation against the new disclosure revision. Generate/Replace never rotate the public reference or change visibility. Two different operation UUIDs using the same expected character revision produce one commit and one stale denial; identical UUID/exact terms produce one commit and a receipt replay, without another revision advance, token or expiry extension.

`account.disclosure.withdraw` is a deliberately narrow out-of-character consent operation. It requires current eligible non-operator Auth and resolves account ownership on the server. Game restriction, incapacitation or dead history do not prevent it. It can only reduce disclosure; it cannot publish a profile, issue a token, edit alias/appearance/life, grant character authority or return a private historical dossier. Its request is account-wide, so it needs no client-selected historical character or stale expected character revision. It locks the account for update and all actual owned character rows in deterministic ID order, checks their current versions and revokes their tokens in the same transaction. **Every new explicit withdrawal advances both character and disclosure revisions and rotates public references for every owned character row**, including an already-private row with no token. This records a refusal barrier that prevents a pending older publication draft from committing after Stop sharing, without a new consent-epoch table/framework. Preserve life, ownership and estate authority unchanged; historical token withdrawal returns only minimal owned-receipt metadata, never a dossier. An already-private withdrawal still records one durable receipt and advances this barrier once. If no linked game account or owned profile exists, return safe unavailability without lazy account/profile creation.

This monotonic operation remains effective after stale UI; no client version exception extends to ordinary publication. A concurrent publisher using an earlier version becomes stale after withdrawal commits even if privacy booleans were already private/off. A later fresh, deliberate confirmed publication may opt in again. Matching withdrawal UUID/exact-terms replay is historical metadata only: it causes no additional bump/rotation and never reapplies withdrawal over that later publication. Amend ADR 0013 narrowly for this consent boundary during implementation.

Resolution checks the independent outward-sharing gate and reader eligibility, then locks current issuer profile/owned state and token in consistent order. An ordinary signed-in receiver needs no creation/disclosure pilot grant and need not have a character; it can view only the projection deliberately shared by the designated issuer. Issuer grant revocation blocks new publication/issuance but does not alone erase prior consent: existing outward reads still independently require the global gate, current issuer eligibility/ownership/truth, current consent and valid reference/token. The grant grants no receiver privileges or search surface, and token possession replaces none of these checks. When reader and issuer identities differ, identify the needed rows without disclosing a result and acquire relevant identity/account locks in canonical order before final checks, so reciprocal profile reads do not take exclusive identity locks in opposite orders. Gate-off, issuer death, **any current issuer operator assignment**, detached/ineligible provider identity, unsupported official-ID state, private visibility, changed disclosure revision, revocation, wrong scope or server-time expiry deny. Preserve operator/player separation even if an old consent or token remains stored. A game-restricted issuer may retain already chosen read-only visibility while the gate is on; they can withdraw it, and cannot newly publish. Incapacitation likewise retains existing read-only disclosure without action authority. Death never creates a public dossier; retain stored historical policy without serving it through this live-card feature.

Issuer restrictions, death, privacy withdrawal, revocation, gate/grant transitions and resolution are tested with competing real database transactions. Lock the external gate for share during new publication/issue and outward reads so a competing gate-off decision linearizes against those transactions. Once withdrawal/revocation/gate-off wins its lock and commits, later resolution denies. A read committed before withdrawal can deliver a snapshot; do not claim that delivery or screenshots can be recalled. Future life/restriction writers must respect the existing lock order and advance appropriate revisions.

## QR lifetime, secret handling and saved cards

The server generates 32 bytes using its CSPRNG and encodes an opaque URL-safe token. Scope is exactly `profile.view`; creation and expiry use database server time, with a fixed **ten-minute** lifetime. There are no client expiry/reward/proximity claims or signed self-contained profile fields. Repeated valid scans are read-only; there is no automatic acceptance or consume-on-view. Generate, Replace and Revoke are explicit actions, with no background refresh or offline queue. Generate requires no currently valid token; if one exists, retrieve confirmed metadata and offer Replace rather than silently replacing it. Replace requires a current nonrevoked invitation and the expected character revision. An expired previous row can be revoked during either eligible explicit issuance flow; a missing/revoked replacement target requires refresh and a deliberate Generate action.

Only the digest is stored. The raw secret is returned once after a new committed issue and kept transiently by the current issuing session. A retry with the same operation returns the same issuance receipt and original expiry without generating a new secret. If the raw token was lost after commit, the interface says **QR issued; code unavailable on this device** and offers explicit **Replace QR** using a new operation UUID/current confirmed revision. This revokes the old token. It never promises a recoverable identical secret from hash-only storage. Reload/sign-out can therefore retain confirmed issuance metadata while losing the displayable QR; the deliberate replacement flow handles that state.

The QR encodes the same-site invitation landing URL with the token in a **fragment**, never a path/query. Capture the expected token format before Router navigation, immediately replace history with the fixed token-free route and keep the value in transient memory. Resolution uses a constant API path and JSON body because current API request logging records paths. No real issued token enters analytics, logs, referer forwarding, permanent browser storage, server-rendered assets, source maps or committed screenshots/fixtures; synthetic nonproduction tokens are appropriate for meaningful tests. Use `no-referrer` for the landing feature and ensure it contains no external resources that could disclose its context. Do not log validation input or token values.

An anonymous landing shows sign-in without resolving. The ordinary in-app sign-in flow may retain the captured token in the current page's transient state, binds post-login resolution to the freshly validated reader and retains no caller-controlled return URL. Recovery/operator/ineligible sessions cannot resolve. Reload or navigation that loses the transient token asks the user to rescan/paste the link; it does not persist a secret to bridge recovery or tabs. Once viewer A is established, switching account clears the token/profile and requires a fresh scan for B. Copy/paste of the complete link is supported through an explicit labeled field and the same strict parser.

No in-app camera dependency is necessary: another phone's ordinary camera opens the URL. The read-only documentation probe recommends pinned **qrcode 1.5.4** (MIT) with development types **@types/qrcode 1.5.6**, installed only after written-spec/plan approval. Use the documented synchronous `QRCode.create` module matrix and render it locally as React SVG: black modules, white background, medium error correction, four-module quiet zone and no logo or decorative reshaping. Avoid injecting generated XML. Official metadata provides a browser entry mapping; this is documentation evidence, not a tested browser bundle or phone scan. [Official API and rendering documentation](https://github.com/soldair/node-qrcode/blob/master/README.md), [official package metadata](https://github.com/soldair/node-qrcode/blob/master/package.json).

Saved cards remain snapshots; the screen says the shared profile is checked when opened and temporary QR expires. Countdown is advisory; expiration decisions are server-side. On confirmed expiration/revocation, session replacement, sign-out or loss of validated state, hide the displayed QR and outward/private content. A connection failure shows unconfirmed/unavailable rather than presenting a stale projection as current. **Conceal ID** clears the on-screen card/QR immediately; it does not imply previously issued links were revoked. **Stop sharing** performs the authoritative withdrawal that prevents future disclosure.

## Player flow and failure handling

Replace `/identity`'s placeholder with a validated owner ID surface. Loading, unavailable service, no living identity, observer, unsupported official ID and expired session have honest distinct owner copy and usable next actions. Ordinary incapacitated/restricted users get read-only card access and **Stop sharing**; they do not get publication or issue controls. The private settings surface shows visibility, two opt-in toggles and an accurate preview. Saving is deliberate and does not occur merely because controls change. Broad historical own-record UI remains excluded.

**Show ID** opens a viewport-filling presentation with large alias/Civilian label, optional disclosed avatar/date, optional currently generated QR, visible expiry state and immediate **Conceal ID**. This uses app layout, not the browser Fullscreen API. Safe areas, 44px touch targets, readable contrast, labels beyond color, focus trapping/return, escape/back handling, reduced motion, 320–440px portrait and phone landscape are required. Body drawer and persistent quick access remain intact. Opening the card never mints a token automatically.

Owner stale-revision errors preserve the exact unsent draft, retrieve confirmed state and require a new deliberate action. Transport failure retains operation UUID and exact submitted draft for explicit retry; changed terms start a new UUID. Matching receipts prevent duplicate effects but historical outcomes do not replace newer settings. Expired sessions require sign-in; unavailable service and rate limiting provide retry actions without claiming success. No offline game mutation replays on reconnect; reconnect retrieves confirmed state first.

Unknown/expired/revoked/tampered/wrong-scope tokens, inaccessible/private/unknown public references, dead/unsupported issuers and issuer-unavailable predicates share a generic **Shared profile unavailable** receiver response, without private reasons or record existence. Reader authentication/session/service failures have the established safe boundary messages; internal errors and private predicate details remain sanitized. Current owner errors may identify their own stale draft or operation conflict, never another owner's state.

Cache keys and rendering bind private owner settings, drafts, issue responses and outward reads to validated user/session/generation. Abort stale reads; reject late mutation/resolve results from replaced accounts before rendering or changing controls. Clear raw tokens and old private data on sign-out/session replacement. Do not import database/server/private content into player code; only contracts, client and UI packages are public dependencies.
