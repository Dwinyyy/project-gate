# Task 2.5 — Character onboarding and System design

**Status:** Conversational design approved by the owner on 2026-09-28; this written specification awaits owner review. Task 2.5 is not implemented.

## Intended experience and boundaries

A verified, non-operator player opens the main site on a phone, chooses an alias and a free visual appearance, creates one durable unawakened character, and then sees that same identity after refresh, sign-out and return. The System home becomes a useful private character overview rather than the foundation placeholder. A persistent quick-access body-status control opens a readable drawer. A character who has not awakened sees **MP: Dormant**. The UI never treats its cached view, a chosen portrait, or an old creation result as authority for another action.

This task extends the existing transactional character service and private `/v1/me` response. It does not implement profiles, privacy controls, fullscreen ID or invitation QR (Task 2.6), dead-character records and observer features (Task 2.7), or authoritative HP, stamina, injuries, poison, bleeding and combat resources (Task 6.4). The drawer shows actual life, awakening and presence state and labels unimplemented resource measurements as not yet tracked. It never invents HP or stamina numbers or implies a rescue or combat action exists.

The owner approved a small library of free visual presets with a few selectable traits, an honest body drawer without premature combat numbers, and a private hosted test-player allowlist guarded by the existing global character-creation switch. Character creation remains unavailable to ordinary public signups while the game is incomplete. Public lethal play remains disabled.

## Approaches and decision

1. **Chosen: versioned free appearance catalog, existing character transaction, private pilot access.** This delivers a visual identity now, preserves retry and one-living-slot guarantees, and permits one real hosted player test without broad access.
2. A detailed character creator would require a much larger asset, validation, editing and moderation surface before the first persistent identity exists. It remains a future cosmetic expansion.
3. Text-only appearance would save assets but would not deliver the visual identity the owner chose. User-uploaded portraits and unrestricted appearance text are outside this first release.

## Appearance and persistence

The first catalog consists of a small, inclusive set of free base portraits plus skin-tone, hair-style and hair-color choices. Choices are not gated by a gender field. Every offered combination must render in the bundled player assets, work without a network image service, and have descriptive labels for nonvisual use. The implementation plan will fix the catalog IDs and asset set; the server accepts only IDs from that fixed catalog, not arbitrary image URLs, CSS, colors, or client-supplied display markup. Future paid cosmetics stay account-level where appropriate and confer no power; no purchase or payment path is added here.

Store the selected catalog version and trait IDs with the durable `game.characters` row through one canonical SQL migration. Database constraints or references must reject unsupported IDs independently of browser controls; the server validates the complete combination before insertion. An existing character's choice must remain renderable if a later catalog changes. Historical characters in other environments must not be silently deleted or made unreadable by the migration; any backfill/default is explicit in the plan and tests. Appearance is private in Task 2.5 and is projected only to the character owner through `/v1/me`. Task 2.6 decides what, if anything, becomes public.

Character creation accepts a canonical alias and one appearance selection. Preserve the existing 1–40-character, nonblank alias rule and reject control characters and unsupported fields; define one server-side normalization used for both storage and retry fingerprinting. The operation fingerprint covers the normalized alias, catalog version and all trait IDs in a stable canonical order. The same operation ID with the same complete request returns its original result after current authorization; reusing it with a different alias or appearance is a conflict. A currently granted tester may replay a previously committed receipt after the global switch is turned off, preserving Task 2.3's confirmed-result behavior, but cannot create a new character then. The appearance choice, character row and receipt commit or roll back together. Existing uniqueness, cooldown, operator exclusion, Auth eligibility, restriction and one-living-character rules remain authoritative.

The private `GET /v1/me` contract advances from schema version 2 to 3 and includes the living character's catalog version and selected appearance IDs. It remains read-only and never creates a game account. It still returns no dead-character dossier, other account or Auth IDs, hidden awakening evidence, precise location or moderation reason. `POST /v1/characters` keeps its safe receipt response; after success the client obtains confirmed character state from `/v1/me`.

## Private hosted pilot

Add a private owner-managed test-player allowlist, keyed to the verified Auth user ID, with an attributable grant/revoke record containing actor, reason, request identity and time. Removing a provider login may remove its pilot grant but must not cascade into the durable game account or character history. The application runtime may read its current decision but cannot add, alter or remove grants; public Supabase roles and clients have no access. Grant or revoke operations use a trusted, audited owner path and must not be possible through editable user metadata or DevTools. The existing `ops.feature_controls.characters` boolean remains an independent global kill switch. New creation requires **both** the switch and an active test-player grant, checked under the same creation transaction and consistent lock order before account or character insertion. The player UI receives only an availability state, not the allowlist or grant metadata.

Revoking a grant blocks a new creation or old creation-receipt replay after the revocation wins the lock. If a creation commits first, later revocation does not erase the resulting character or rewrite its history. The guard still excludes any active or suspended operator assignment and any restricted or provider-ineligible login, even if that Auth ID is allowlisted. An allowlisted account does not gain moderation, gameplay or operator authority. For ordinary users, unavailable creation has the same safe response regardless of whether the global switch is off or their grant is absent.

Keep the global switch off while the migration and application are reviewed and deployed. After green checks and managed read-back, grant one designated non-operator test account through the audited owner path, turn the switch on for the private pilot, and verify that a second ordinary verified account still cannot create. The public status page must not advertise broad character availability because the pilot switch is on. The owner supplies passwords, email verification and any private account interaction directly in the site; no credentials or recovery links enter project notes or tool output.

## Mobile System and body-status flow

An anonymous visitor sees a clear sign-in route and no private character query. During Auth validation, the existing compact themed check remains; once validated, the client fetches `/v1/me` with the current bearer. An eligible onboarding player gets a phone-friendly alias and appearance form with an explicit final creation action. Disabled, cooldown, occupied, restricted, observer, incapacitated, unavailable service and expired-session states each have accurate copy and available next actions. There is no button that silently bypasses the server's current availability result.

For an active character, System shows the selected portrait and alias, registered origin date, unawakened/awakened label, current life and presence state, and access to body status. It can show future modules as unavailable with honest explanations; it must not fabricate rank, class, items, objectives or rewards. An incapacitated character gets a visible read-only condition without ordinary action controls. A restricted account may view its own current character overview but cannot create or act; support remains a future feature. An observer gets a safe read-only handoff and no dead dossier or new action UI until Task 2.7. Operator sessions still redirect to the restricted operator route before any player data fetch.

The body-status control is persistent and easy to reach on narrow screens. The drawer presents real life, awakening and presence values. It shows **MP: Dormant** only while unawakened; an awakened fixture with no resource model gets an honest unavailable value. HP, stamina, injuries and effects are labeled not yet tracked until Task 6.4 provides authoritative data. It uses labels and icons as well as color, supports keyboard and screen-reader focus/return, reduced motion, short viewports, mobile safe areas and touch targets. The System and onboarding screens remain usable at 320px and 390px widths and on desktop.

## Request, retry and privacy behavior

The player client validates the returned contract, keys private character state to the currently validated account/session without putting a raw access token into cache keys or logs, and clears or isolates it immediately on sign-out, account replacement, operator routing or invalid session. A late response for a prior account cannot paint that account's character into the new session. Browser history and generic error views must not expose private character details. Private API responses keep `Cache-Control: no-store` and request IDs.

The first explicit submit creates a stable operation UUID for that exact normalized draft. While its outcome is uncertain, controls prevent accidental duplicate taps. A network failure or refresh retrieves confirmed `/v1/me` state first. A retry happens only after an explicit user action and uses the same UUID and same draft; editing the draft starts a new UUID. No offline creation command is queued for silent replay. Conflict, cooldown, disabled, restriction and session failures have distinct, non-secret messages with safe retry/sign-in paths. The server remains authoritative even if the UI displayed an older eligibility state.

## Verification and completion gate

Use focused unit/API tests and real disposable PostgreSQL tests for catalog/alias validation, migration backfill, narrow grants, allowlist grant/revoke and creation races, operator/provider/restricted denials, exact idempotent replay and conflicting drafts, one-living-slot contention, and rollback. Browser tests cover real signed-in flow with controlled Auth responses, refresh, account switching and late fetches, explicit retry/offline behavior, accessible drawer, keyboard, and narrow/short layouts. Preserve the existing registration/recovery/operator journeys. Use current dependency documentation through Context7 only where version-specific React Query, Supabase, Fastify or other API behavior materially affects implementation.

Before managed changes, obtain independent Sol review and green local/CI checks; apply only the reviewed canonical migration, read back checksum, grants, allowlist and flag. Verify the exact deployed API revision and anonymous boundaries. A real allowlisted non-operator account must then create one character on the hosted main site, refresh and sign out/in to recover the same persisted identity; a second creation and an ordinary nonallowlisted account must be denied. Give the owner precise current click-by-click steps when private email/password interaction is required. Record which steps the agent observed and which the owner reported. Do not mark Task 2.5 or Phase 2 complete based on mocks or a rendered shell.
