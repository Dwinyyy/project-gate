# Task 2.3 — Transactional character creation and eligibility

**Status:** Approved by the owner for Task 2.3 implementation, 2026-09-27. No Task 2.3 API or database mutation has been implemented.

## Intended outcome and scope

A verified player can learn whether a new character may be created and, when enabled, create one durable, unawakened civilian identity. Concurrent or repeated requests cannot create a second living character. A previously dead character remains private history; an incapacitated character still occupies the living slot. Server time and current database state decide cooldown and eligibility. The owner chose an **operator-only login**: an account assigned as an operator cannot create or play a player character using that login. Changing the page or request body cannot change these rules.

Task 2.3 adds the account-link service, read-only eligibility API, transactional creation API, retry receipt, and narrow database grants. Task 2.4 owns operation-specific authority for later actions. Task 2.5 owns onboarding, appearance selection, System presentation, and usable character UI. The managed `characters` feature control remains off during this task, so the hosted foundation does not become playable merely because an API route exists.

## Approaches considered

1. **Server-owned transaction with a private receipt — selected.** The existing API verifies the live Supabase session, then a single PostgreSQL transaction resolves or creates the durable account, checks eligibility, inserts the character, and records the request ID. The receipt makes a lost-response retry return the same committed identity. This uses the existing private `hunter_runtime` connection and partial unique index.
2. **Expose the `game` schema through Supabase Data API or an RPC.** This reduces API code but widens the public API surface and makes it harder to keep account linking, cooldown, operator exclusion, and operation identity in one established server boundary. `game` remains unexposed.
3. **Check eligibility in the client, then insert.** A stale or modified client can race another request or omit the check, so this cannot own the rule.

## Identity and API boundary

The API accepts only a provider-verified **standard password session** from the existing Auth verifier; recovery and other restricted sessions cannot call character endpoints. The verifier must validate and reject malformed provider-account status fields and reject a currently banned, soft-deleted, or anonymous Supabase user, including when that user still holds an earlier valid access token. The provider's current user ID, not email, editable metadata, client account ID, or a cached character ID, identifies the login. Email must be verified. A missing, expired, invalid, or revoked session receives a safe denial. No service-role key goes to the client.

Any record in `ops.operator_accounts`, whether active or suspended, makes that login operator-only for character APIs. A suspended operator must not silently fall through to player character access; the existing session-routing response must likewise avoid describing it as a playable player login. Operator assignment does not delete a preexisting character or transfer it to another login. A separately audited administrative decision would be needed to detach or recover the game account.

`GET /v1/me` is read-only. It returns a versioned, owner-only projection with the linked game account's current living character, if any, and a creation eligibility state: `available`, `occupied`, `cooldown`, or `feature_disabled`. Cooldown may include the server-stored next-eligible time; no private history, hidden awakening evidence, precise location, other account ID, or provider token is exposed. The endpoint never creates an account row. When the character control is off, eligibility is `feature_disabled` regardless of slot or cooldown, while a linked current character may still appear in the private projection. `available` is returned only when a new creation can pass the current flag, slot, and cooldown checks. Operator-only and unverified identities receive stable denials instead of a player projection. API failures are distinguishable from genuine ineligibility and never turn into an optimistic `available` result.

`POST /v1/characters` accepts a display alias and a required client-generated UUID operation ID in `Idempotency-Key`. It accepts no account, Auth, character, lifecycle, cooldown, rank, reward, time, or location claim. The API validates the alias against the existing database length/nonblank constraint and a bounded request size; richer naming and appearance policy belongs to Task 2.5. A **currently authorized** replay returns the same private character ID and creation result; authentication, verified email, and the operator-only rule are checked before any historical receipt is disclosed. This receipt is not a current-life or action-authority claim; `GET /v1/me` supplies current state. Reusing an operation ID with different content returns a conflict, never a second character. The API does not silently replay offline queued mutations; a user-triggered retry with the same operation ID is permitted after an uncertain response.

## Transaction and persistence

One new canonical SQL migration creates `game.character_creation_receipts`, keyed by game account and operation UUID, with a request fingerprint, resulting character ID, and creation time. It references the durable account and character without cascade deletion. Only the private runtime role can read and insert receipts. Grant `hunter_runtime` the account/character inserts and **column-scoped `UPDATE (revision)` on `game.accounts`** needed for PostgreSQL `SELECT ... FOR UPDATE` row locking; creation itself does not change the revision. Grant `UPDATE (singleton)` on `ops.feature_controls` solely to permit a `FOR SHARE` lock on its one constrained `singleton = true` row; the service never changes the flag or this column. This serializes a flag-off update with an in-flight creation so one operation cannot commit after the disabling update has committed.

The migration also adds one narrowly scoped, private `SECURITY DEFINER` routine that checks the matching `auth.users` row for verified email, no active ban, no deletion, and non-anonymous status using database wall time, and holds a `FOR SHARE` lock until the creation transaction ends. Its owner must already be authorized to read and lock `auth.users`; it uses a fixed safe search path, accepts only a UUID, returns only an eligibility boolean, and has `PUBLIC` execution revoked in the same migration before granting execution solely to `hunter_runtime`. The runtime role receives no direct `auth.users` privileges. The transaction lock orders a concurrent provider ban, deletion, or verification change before or after creation, rather than allowing a stale provider response to authorize a later commit. Runtime gains no account-link reassignment, cooldown update, lifecycle update, character deletion, feature-toggle update, or public-schema access. Public API roles retain no `game` privileges. The migration must leave `ops.feature_controls.characters = false` and preserve prior migration checksums.

The creation service runs through the shared database transaction helper:

1. Verify the live Auth identity before transaction entry. Inside the transaction, take the audited operator-assignment lock with the parameter cast to canonical UUID text: `pg_advisory_xact_lock(hashtextextended('operator-account:' || $1::uuid::text, 0))`. Then recheck whether **any** operator row exists. Lock the `ops.feature_controls` singleton row with `FOR SHARE`, and call the private Auth-eligibility routine to lock and recheck current provider-account state; any denial rolls back. A concurrent owner flag update or provider-account update either waits for this transaction or is observed before creation. Resolve the game account only by the verified `auth.users.id`; never search or attach by email. If no account exists and the character control is off, deny without creating one. Otherwise insert exactly one new account linked to that UUID, using the unique Auth-link constraint to serialize simultaneous first requests.
2. Lock the resolved account row. Look up the operation receipt before checking eligibility: an exact committed retry returns its original character even if a later flag or cooldown change would block a new creation. A changed payload with the same operation ID is rejected.
3. For a new operation, recheck the character control inside the transaction, compare `character_creation_not_before` with database wall time **after the lock wait**, and check for any `alive` or `incapacitated` character. PostgreSQL's partial unique index is the final race guard. Create a character with `alive`, `unawakened`, `sheltered`, and `private` values and insert its receipt in the same transaction. A failure rolls both back. Translate a race or unique violation into a stable occupied/retry response without leaking SQL or account identifiers.

The implementation must make the flag check and account lock order explicit and test their behavior under concurrency. It must not use client clocks or treat an unknown database result as a successful creation. After a successful create, `GET /v1/me` retrieves the committed identity; after a lost response, retrying the same operation ID retrieves the receipt. If the Auth user is deleted, its game-account link becomes null as Task 2.2 established, and a later new Auth UUID with the same email receives a new account, never the detached history. Account recovery or reassociation needs a later audited design.

## Denials and release behavior

Invalid authentication returns 401; recovery, restricted, unverified, and operator-only logins receive distinct safe 403 codes. Disabled character creation returns a stable unavailable response without writing a character. Occupied, cooldown, and changed-operation conflicts have distinct machine-readable codes and retry guidance; the response never discloses another account's data. The read endpoint must distinguish unavailable service from a legitimate `available` state. Rate limits, no-store responses, bounded bodies, request IDs, and sanitized server logs follow the existing API conventions. No character endpoint appears in the player UI until Task 2.5.

The `characters` control stays off in managed development. Disposable PostgreSQL/API tests may enable it within their isolated database; no manual production character row or privilege grant is used to demonstrate the feature. Before a later release turns it on, Tasks 2.4–2.5 must add action authority, onboarding, error handling, and real end-to-end verification.

## Verification

Focused tests on real disposable PostgreSQL must cover first link creation, idempotent same-key replay, changed-payload conflict, simultaneous same-key and different-key requests, one living slot including incapacitation, dead-history retention, cooldown before/after boundary using database time, Auth deletion and same-email/new-UUID isolation, unverified/recovery/restricted/operator/suspended-operator denial, an already-issued token after a ban, assignment-versus-creation and provider-ban-versus-creation in both lock orders, flag-off-versus-creation in both lock orders, and rollback without orphan receipts. Check direct public-role denial, successful account `FOR UPDATE` and feature-control `FOR SHARE` locks under the real `hunter_runtime` role, and precise runtime grants that deny changes to Auth links, cooldowns, lifecycle columns, and the feature toggle. Prove only `hunter_runtime` can execute the Auth-eligibility routine, including on a database with public Supabase roles. API tests must exercise authenticated read/create responses, malformed inputs, `GET /v1/me` with no account and the flag off, other feature-disabled behavior, safe errors, and `/v1/auth/session` classifying suspended operators as non-player, through the actual server boundary. Run relevant unit, integration, type, lint, format, boundary, secret, and build checks; obtain independent review before a managed migration and document the exact deployment state. Browser tests remain regression evidence until onboarding exists.

## Follow-on ownership

- **2.4:** current actor, life, account restriction, observer, incapacitation, and dead-character authority for every later operation. Task 2.3's eligibility does not grant those actions.
- **2.5:** accessible mobile onboarding, appearance and alias UX, System panel, body-status drawer, and player-facing recovery from loading, offline, duplicate, and cooldown states.
- **Later death work:** calculate and set cooldown from authoritative death evidence; Task 2.3 reads the stored account timestamp but does not finalize death or change estates.

## Documentation basis

This design follows [the approved Task 2.2 identity spec](2026-09-27-game-account-character-schema-design.md), [ADR 0011](../../adr/0011-durable-game-account-identity.md), [Brief §04 and §20](../../product/brief-source.md), and [the master blueprint's Phase 2](../../plans/master-blueprint.md). PostgreSQL 17 documents that `SELECT ... FOR UPDATE` locks selected rows and requires `UPDATE` on at least one selected-table column, and that `INSERT ... ON CONFLICT DO NOTHING` can handle unique conflicts. Its time-function reference distinguishes transaction-start `current_timestamp` from advancing `clock_timestamp()`. These details matter for runtime locking, first-link races, and cooldown checks after a lock wait: [SELECT](https://www.postgresql.org/docs/17/sql-select.html), [INSERT](https://www.postgresql.org/docs/17/sql-insert.html), [date/time functions](https://www.postgresql.org/docs/17/functions-datetime.html). [Supabase Auth's user model](https://github.com/supabase/auth/blob/master/internal/models/user.go) exposes the current ban, deletion, and anonymous-account fields required for the verifier's fail-closed check.
